# Epic 2 Context: An underwriter gets a cited, auditable suggested verdict

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Facts are extracted from the pages that passed the gate or were accepted in triage, each with its page and a quote checked in code. The verdict agent searches the synthetic underwriting manual and suggests a verdict whose every reason cites facts and manual rules. The underwriter reads it beside the redacted PDF, follows every citation, and can query the agent's log of searches and rule reads. Only retrieval row `r3` is built here. With Epic 1 this completes the end-to-end demo path (demo-ready by the weekend of 10 October 2026; cuts favour that path over breadth). There is no UX design and no architecture principles document; both were skipped on purpose. The services `extraction`, `retrieval` and `verdict` have no folder under `services/` yet; this epic creates them.

## Stories

- Story 2.1: Synthetic underwriting manual and rule table
- Story 2.2: Manual ingested into pgvector as smart chunks
- Story 2.3: Search the manual for rules
- Story 2.4: Fact extraction with checked quotes
- Story 2.5: Suggested verdict with cited reasons
- Story 2.6: Rules that send a case to the underwriter
- Story 2.7: Result view with clickable citations
- Story 2.8: Query the agent's log

## Requirements & Constraints

- **Synthetic data only.** The manual is original text, modelled on the structure of public field impairment guides (impairment, key questions, probable rating); nothing is copied from any carrier's or reinsurer's manual. About 200 pages with prose, tables and cross-references, generated from a rule table of about 40 impairments. Each rule has a `rule_id`, an impairment, a threshold, a debit percentage or decline, and the public source its threshold rests on.
- **The rule table is the answer key.** It lives in `data/answer-key/`, is never indexed, and no service can read it. Each rule is defined in exactly one place in the manual; other mentions are cross-references.
- **Facts:** each has its page, page number (1-based) and a verbatim quote. A quote is verified only by code, against the page text. An unverified fact is stored and flagged, never dropped and never shown as verified. A masked value such as `[Person]` is never extracted as a fact.
- **Verdict:** `standard`, `loaded` (with a loading), `decline` or `refer`. Every reason cites one rule and one or more facts; a reason citing something the agent did not see in that run is not stored. Uncited claims are never shown as findings.
- **Refer rules are code, not prompt:** no matching rule, conflicting rules, an unverified quote on a deciding fact, the step limit reached, or confidence under the floor (default 0.70) gives `refer` with its system reason code. Otherwise: any cited rule that says decline gives `decline`; cited debits give `loaded` with the loading as their sum; no debit gives `standard`.
- **The AI never decides.** The verdict is a suggestion; the payload and the result screen carry the exact label "AI suggestion, not a decision", and no service stores a final decision.
- **A verdict run needs every page in a final status**; while a page waits for a person it is refused with 409.
- **Audit:** extraction and verdict each add an event with actor and time (`facts.extracted` per page, `verdict.suggested` per run, referencing the run). The agent's step log is append-only, one row per tool call, readable by run and by case with `tool` and `rule_id` filters, through the API and from the audit view.
- **Retrieval must stand up to a RAG expert:** one rule per chunk, hybrid search with rank fusion, and a named query from the rule table must bring its rule back in the top 5. Epic 3 measures recall with a fixed query builder, apart from verdict accuracy; nothing built here may make that comparison unfair (same chunks, vectors, embedding model and chat model for every row).
- **Logs and traces** carry ids, codes and timings, never page text, quotes or fact values.
- **Stage commands** are idempotent and finish or fail within 180 seconds; a repeat returns the stored result with no new model call.
- **Quality gates** as in Epic 1: a test named for its story per acceptance criterion; coverage 80% services, 60% SPA; unit tests on fakes, integration tests on the containerised database; exact pins and lock files; server-side validation; AI behaviour is judged by the eval set, not coverage.

## Technical Decisions

- **Environment is down while coding (owner rule):** do not bring Azure up to test a story. Build every story in every epic first and prove it locally (unit tests, integration tests against the containers in `compose.yaml`, the local Dapr start). Work only Azure can prove is written against fakes or stand-ins, and its Azure check is added to `deferred-work.md` for one final test session. In this epic that covers Document Intelligence layout parsing of the manual, embeddings, the chat model for extraction and the verdict agent, the ingestion job and the `manual` container, and the three new services' deploy, identities and database bootstrap. A cycle costs about 11 minutes up and 32 down.
- **Services and data:** `extraction` owns facts and quote-check results; `retrieval` owns manual chunks, embeddings and the manual PDF (Blob container `manual`); `verdict` owns verdict runs, reasons and `verdict.agent_step`. One schema and one database role each, Alembic per service, no cross-schema access. Same layout as the Epic 1 services (`domain/` framework-free, `adapters/`, `prompts/`, `migrations/`, `tests/`, one settings object with the app id as env prefix).
- **Allowed calls added here:** `workflow` to `extraction` and `verdict` (commands); `extraction` to `intake` (page text); `verdict` to `extraction` (facts) and `retrieval` (search, rule read); `web` to `extraction`, `verdict` and `retrieval` (reads). Nothing else. Only `workflow` sequences; `verdict` never starts itself.
- **Operations and keys:** `POST /fact-sets` keyed by `case_id` + `page_id`; `POST /verdict-runs` keyed by `case_id` + `retriever_config`; `web` to `workflow` `POST /cases/<case_id>/verdict-runs` (409 until every page is terminal); `GET /cases/<case_id>/facts`; `GET /cases/<case_id>/verdict-runs`, `GET /verdict-runs/<id>/steps`, `GET /cases/<case_id>/agent-steps?tool=&rule_id=`; `POST /searches` (not stored, no key); `GET /rules/<rule_id>?retriever_config=` (without the parameter, the `smart` chunk; unknown rule 404). Commands carry ids and small summaries only.
- **The stage pattern Epic 1 built, to be followed by extraction and verdict:** the stage inserts its key row as `running` before any work; one 180-second deadline covers the whole command (`workflow`'s activity timeout is 200 s); the finished result is stored together with its audit record and returned again on a repeat; a repeat while running is 409 `in_progress`. A failed result is a 200 with `status: failed` (it is the stored result, and `workflow` records it); only `in_progress` and `not_found` are errors to the caller. A `running` row older than the deadline plus a stale margin is settled as failed (`stage_timeout`) by the next repeat, which does not take the work over; a late finish is written only while the row is still `running`. On a fault that passes (the upstream service unreachable, or the request cancelled) the key row is released so the same command sent again does the work. What can be refused without work (unknown page, bad parameter) is checked before the key row. `workflow` retries stage commands under a policy of their own that outlasts the deadline plus the stale margin, and records a failed stage in the recording of its result (one `stage.failed` event).
- **Model gateway:** one gateway module per service, on the `openai` SDK against `<endpoint>/openai/v1/` with an Entra token (`https://cognitiveservices.azure.com/.default`); deployment names only as settings. It retries 429, 5xx, 408 and 409 with backoff (honouring `Retry-After`, capped waits, a random part), then raises `model_unavailable`; other 4xx are not retried. It opens a span per call, puts token usage on the span and in one log line, and holds a process-wide cap on concurrent calls. The gateway returns text; the domain parses it into a contracts model, and a failed parse is a failed result (`invalid_model_output`), never passed on. Adapter spans go through the service's `adapter_span` helper (no exception messages, database parameters hidden). The chat deployment's 100 thousand tokens a minute are shared by classification, extraction and the verdict agent.
- **Dev-only stand-ins live in `packages/synthdata`** (the Language and model stand-ins, with failure modes); services refuse a plain-HTTP endpoint that is not on loopback, so a stand-in can never be the endpoint in Azure. The model stand-in answers chat completions only; this epic needs it to serve what extraction, the verdict agent, embeddings and the manual's layout parsing ask for.
- **Guard from story 1.4:** nothing under `services/` (tests included) may name `synthdata` or the answer key. Tests that run a stand-in, read the answer key, or run several real services together live in `packages/synthdata/tests/`; service tests use fakes.
- **Audit:** `workflow.audit_event` stays the only audit table, written by `workflow` in the transaction of the status change, unique on case, page, action and reference. Epic 1 added a tenth action, `page.routed` (actor `workflow:gate`, detail `route` and `threshold`), so every page status change has an event; `extracting` to `extracted` must have its `facts.extracted` likewise. The audit record cannot yet carry a failed stage's error code.
- **Case status follows the pages (story 1.10):** one domain rule works the case status out from the stored pages, under the lock on the case row. It runs in every decision and in the settle after the gate, not yet in the recording of a stage result. Story 2.4 must apply it there, so the last page reaching `extracted` completes the case or hands it to the verdict stage. A page reaches `extracted` only from `extracting`; a failed page stage fails the whole case.
- **Conditions on story 2.4 (recorded in `deferred-work.md`):** (1) before extraction follows an accept, `workflow` itself must wake an orchestration whose decision is stored but whose event was never raised (today only a repeat of the same decision from the browser raises it), and end the orchestration of a case that failed while it waited; (2) cases now wait for people, and a waiting case is replayed from its history, so a change to what `case_lifecycle` yields (an activity added, removed or reordered, another event name) is registered as a new orchestration name beside it, or deployed only when no case waits. Extraction after the wait is such a change.
- **Lifecycle:** each activity is one stage call; a verdict run asked for after the case finished is its own orchestration, instance id `<case_id>:verdict:<retriever_config>`. A case is started with a list of `retriever_configs` (default one, from a setting) and gets one run per entry on the same facts.
- **Quote check:** `extraction` reads only `intake`'s stored page text. A fact is `quote_verified` only when the normalised quote is found in the normalised page text, using the one normalisation function in contracts (it keeps mask tokens). Verified facts carry `quote_start` and `quote_end`. Open from story 1.1, for story 2.4: add one shared function that finds the quote and returns offsets into the raw page text, and state the offset unit, because `intake` turns an offset range into word boxes. Also unchecked: the stored text order of a table or multi-column page.
- **Ingestion:** a one-off, idempotent job on the `retrieval` image and identity, started by the pipeline, calling no other service. It parses the manual PDF with Document Intelligence's layout model. A `smart` chunk holds exactly one rule, its parent section id, an LLM-written context line, the manual page and a 3,072-dimension `text-embedding-3-large` vector; `rule_ids` are only rules defined in the chunk, never ones it refers to. `chunk_id` is stable across reruns (Epic 3 loads the same records into Azure AI Search and adds the `fixed` set). Exact nearest-neighbour search, no approximate index. The definition marker `Rule <rule_id>:` and the pattern `UW-[A-Z]{2,4}-[0-9]{3}` come from contracts.
- **Search:** one operation for every ladder row: query, `retriever_config`, `top_k` (default 5) in; `retriever_config`, `latency_ms` and ranked items out (`chunk_id`, `rule_ids`, `rank`, `score`, `text`, `manual_page`, `impairment`). `r3` is vector plus PostgreSQL full-text, fused with reciprocal rank fusion. No row gets its own endpoint or shape.
- **Verdict agent:** built with Microsoft Agent Framework inside `verdict`, with exactly three tools: `list_facts` (case fixed by the server), `search_rules` (query text plus the `fact_id`; `retriever_config` fixed by the server) and `read_rule` (only a `rule_id` returned by a search, or referred to by a rule already read, in the same run; otherwise refused). It writes only its own run. Every tool call is appended to `verdict.agent_step` (`verdict_run_id`, `case_id`, `step_no`, `tool`, `arguments`, `fact_id`, `rule_ids`, `latency_ms`, `occurred_at`). A run stops at a configured step limit. Output: `verdict`, `loading_pct` (null unless `loaded`), `confidence`, `reasons` (`rule_id`, `fact_ids`, `effect` of `none`, `debit` or `decline`, `debit_pct`) and `system_reasons` (`no_matching_rule`, `conflicting_rules`, `unverified_quote`, `low_confidence`, `step_limit`).
- **Contracts gaps to close in one change with the affected services (stories 2.5 and 2.8):** the agent step has no outcome or error field (a refused `read_rule` has nowhere to go), verdict-run payloads carry no failure reason, the verdict-run request has no run id, and list responses are unbounded.
- **Conventions** as in Epic 1: UUIDv7 ids generated by the owner; `snake_case` with the same field name in database, API and SPA; singular table names; ISO 8601 UTC; confidence and scores as 0-to-1 floats; a loading or debit is an integer percentage; error shape `{"error": {"code", "message", "trace_id"}}`. Pins include `agent-framework-core` 1.20.0, `agent-framework-openai` 1.15.0, `pgvector` 0.5.0 and `react-pdf` 11.0.0.
- **Infrastructure:** each new service is one image, one Container App held at one replica (so its own cap on model calls is the cap for the environment), one identity (Foundry User for `extraction` and `verdict`; for `retrieval` also Document Intelligence and the `manual` container) and one Dapr app id, added to the `app` stack, the local multi-app run file and the database bootstrap steps. The deploy still has no migration step; each new migration joins the manual database step of the final session.

## UX & Interaction Patterns

- No design system; plain default styling. The result view has two panes: the redacted PDF on the left; on the right the verdict, then the reasons, then the facts, with the fixed label "AI suggestion, not a decision".
- Selecting a verified fact's citation scrolls the PDF to its page and highlights the quote by drawing the word boxes `intake` returns for the fact's offsets; the SPA never searches the browser's own text layer. An unverified fact is visibly flagged and has no highlight.
- Selecting a reason's `rule_id` opens the rule's text, impairment and manual page beside it.
- In the audit view, a "verdict suggested" event opens that run's steps as a drill-down: step number, tool, arguments, fact, rules returned or read, latency and time, in order.
- `web` assembles each screen from the owning services and holds no business rules; the SPA polls through its one API client, sends `X-Demo-Role` on every call (so files and images are read by the client, not by plain elements), keeps user-facing text in the strings module, and never renders model output as HTML. These are underwriter screens.

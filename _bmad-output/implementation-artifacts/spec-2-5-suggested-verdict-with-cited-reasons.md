## Intent

**Problem:** A case ends with checked facts and nothing more: nobody suggests what they mean for the application, and no suggestion could be audited if one did.

**Approach:** Build the `verdict` service. Its agent, with exactly three tools, reads the case's facts, searches the manual and reads rules, and proposes reasons; every tool call is logged. `verdict`'s domain code, not the prompt, decides what is stored: only reasons whose facts and rules were seen in the run, the refer rules, and the verdict and loading worked out from the cited rules. `workflow` commands one run per retriever configuration once every page is final, and the case completes after them. Stories 2.5 and 2.6 are built together because the second is the domain half of the first.

## Boundaries & Constraints

**Always:**
- Spine AD-15, AD-10, AD-16, AD-11, AD-6, AD-8, AD-3; the stage and model-gateway patterns as the epic context states them. `POST /verdict-runs` is keyed on `case_id` + `retriever_config`; reads are `GET /cases/{case_id}/verdict-runs`, `GET /verdict-runs/{verdict_run_id}/steps` and `GET /cases/{case_id}/agent-steps?tool=&rule_id=`.
- The agent is built with Microsoft Agent Framework and has exactly three tools. `list_facts`: the case is fixed by the server. `search_rules`: a query and the `fact_id` it is about; the `retriever_config` is fixed by the server. `read_rule`: only a `rule_id` that a search of this run returned, or that a rule already read in this run refers to; any other is refused and the refusal is logged as a step. Tool arguments are validated server-side; the model never names a case, a run or a retriever row. Every model call goes through the service's one gateway (retries, the concurrency cap, spans, token usage).
- Every tool call, refused ones included, is one appended row of `verdict.agent_step` (run, case, step number, tool, arguments, fact, the rules returned or read, outcome, latency, time). The table is append-only for the service's database role. A run stops at a step limit (a setting).
- What is stored is decided by domain code from the agent's proposal:
  - a reason is kept only if its rule was seen in this run (returned by a search or read) and every one of its facts was listed in this run; and only if its effect agrees with the rule's text as the run read it (a decline needs a rule that says decline; a debit needs that percentage in the rule's rating). A dropped reason is counted, never stored, never shown.
  - system reasons: `step_limit` when the limit stopped the run; `unverified_quote` when a kept reason with a debit or decline cites a fact whose quote is not verified; `low_confidence` when the agent's confidence is under the floor (a setting, default 0.70); `no_matching_rule` when the agent reports it, when the case has no facts, or when the agent proposed reasons and none could be kept; `conflicting_rules` when the agent reports it or when kept reasons cite the same fact with rules of one impairment that cannot both apply.
  - the verdict: any system reason gives `refer`; otherwise a kept decline gives `decline`; otherwise kept debits above zero give `loaded` with `loading_pct` their sum; otherwise `standard`. A rule whose rating is no debit is effect `none`. The agent's own verdict word is never stored.
- A run's payload carries the exact label "AI suggestion, not a decision". No service stores a final decision.
- The audit record of a done run is `verdict.suggested`, actor `verdict:<chat deployment name>`, case-level, ref the run's id.
- `workflow`: when every page of a case is final, it commands one run per entry of the case's `retriever_configs`, records each, and only then completes the case. A failed run fails the case. `POST /cases/{case_id}/verdict-runs` on `workflow` asks for one more run on a finished case, as an orchestration of its own (`<case_id>:verdict:<retriever_config>`), and is refused with 409 `pages_not_terminal` while a page is not final.
- Contracts gaps closed here, with every caller: an agent step's outcome (done or refused, with a code); bounded step and run lists that say when more exist; the run id on what a requested run answers.
- Logs carry ids, codes, counts and timings: never fact statements, quotes, queries, rule text or the model's output.

**Never:**
- No fourth tool, no other Foundry tool or connection, no direct database or blob access by the agent. No row `r6` behaviour (Epic 3). No `web` route or screen (stories 2.7 and 2.8).
- The answer key is not read; tests against it live outside `services/`.
- Do not bring Azure up, plan or apply Terraform, or run any `az` or `gh` command that changes something. Do not edit `infra/demo/foundation`. No stand-in ships in a service image.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Loaded | Facts meeting rules with debits +50 and +25, none declining | Run `done`: `loaded`, `loading_pct` 75, a reason per rule with its facts, effect `debit` and `debit_pct`; `verdict.suggested` event | N/A |
| Decline | A kept reason whose rule says decline | `decline`, no loading | N/A |
| Standard | No kept debit or decline, no system reason (a healthy case, or only no-debit rules) | `standard` | N/A |
| Reason cites the unseen | A reason with a rule never returned or read, or a fact never listed | That reason is not stored; the count is logged | If none remain: `refer` with `no_matching_rule` |
| Effect not in the rule | A reason says +100 where the rule read says +50, or decline where it says a debit | That reason is not stored | As above |
| `read_rule` not allowed | A rule id neither returned by a search nor referred to by a rule read | The call is refused; a step with outcome refused is logged; the run goes on | N/A |
| `read_rule` by reference | A rule referred to by a rule already read | Allowed | N/A |
| Unverified quote | A kept debit or decline cites an unverified fact | `refer` with `unverified_quote` | N/A |
| Low confidence | Confidence 0.6 with the floor at 0.70; exactly 0.70 | `refer` with `low_confidence`; at the floor it is not low | N/A |
| Step limit | The agent keeps calling tools | The run stops at the limit: `refer` with `step_limit` | N/A |
| Conflict | Two kept reasons on one fact from bands of one impairment | `refer` with `conflicting_rules` | N/A |
| No facts | A case whose pages were all discarded or denied | `refer` with `no_matching_rule`, no model call needed | N/A |
| Invalid final answer | Not the contract's shape | Run `failed` with `invalid_model_output`; no reasons stored | Case fails with `stage.failed` |
| Tool's service down | `extraction` or `retrieval` unavailable after the client's retries | Run `failed` with `upstream_unavailable` | As above |
| Model unavailable, deadline, repeat while running, repeat after the end | As for the other stages | `model_unavailable`, `stage_timeout`, 409 `in_progress`, the stored run with no model call | As for the other stages |
| Row not built | A command with `r5` | Refused; not retried; the case fails | 409 `retriever_not_available` passed on |
| Case completes | Last page final, one configuration | One run recorded, then `case.completed` | N/A |
| Run asked too early | `POST /cases/{id}/verdict-runs` with a page awaiting a person | Refused | 409 `pages_not_terminal` |
| Run asked again | The same configuration on a finished case | The stored run; no second run | N/A |
| Read the log | Steps by run; by case with `tool` or `rule_id` | Steps in order; only matching ones with a filter | 404 for an unknown run |

## Implementation Notes

- **Contracts.** `StepOutcome` (`done`, `refused`, `failed`) and `AgentStep.outcome` with an `error_code` set when, and only when, the call was not done (`rule_not_seen`, `validation_failed`, `not_found`, and `step_limit`, a new code of the catalogue, for a call the limit stopped; `upstream_unavailable` or `retriever_not_available` for a failed call, `stage_timeout` or `internal_error` for one cancelled or failing half way). `VerdictRunList.has_more`, `AgentStepList.has_more`. `VerdictRunRequested.verdict_run_id` (null while the run runs) and `error_code` (set when, and only when, the run failed). `contracts.audit.VerdictDetail`: the detail of a `verdict.suggested` record names its `retriever_config`, and the record is not valid without it. `VerdictRun.confidence` may be null for a done run in which the agent gave no answer (no facts, step limit); `system_reasons` are set when, and only when, the verdict is `refer`; a run that is not done has no reasons. `SearchRulesArguments.query` is at most 2,000 characters. Schema and SPA types regenerated. No caller outside `verdict` and `workflow` used the changed models.
- **`services/verdict/`** (port 8006, Dapr app id `verdict`, sidecar 3506 locally) has `extraction`'s shape and imports nothing from it. Domain, framework-free: `state.py` (what a run listed, found and read), `toolbox.py` (the three tools: arguments validated with the contracts' models, case and row fixed by the server, the `read_rule` permission, one logged step per call, the step limit), `effects.py` (the rating read off a rule's definition in the three forms the manual prints), `decide.py` (keep or drop, the system reasons, the verdict and the loading; the agent's verdict word is validated and thrown away), `run.py` (the stage operation and the three reads). The prompt (`prompts/suggest_verdict.md`) says how to use the tools and what to answer; nothing it says is stored as given.
- **Agent Framework and the gateway.** `adapters/agent.py` builds an `agent_framework.Agent` per run on an `OpenAIChatCompletionClient` that is handed the gateway's own client. `adapters/model.py`'s `GatewayClient` is an `openai.AsyncOpenAI` whose `chat.completions.create` is `ModelGateway.complete`: so every chat completion the framework makes is retried on 429, 5xx, 408 and 409 with the same waits as the other services, held by the process-wide cap, has its span and its per-attempt span with token usage, and one `model call` log line; the gateway also sets the deployment and `max_completion_tokens` whatever the framework asks, and refuses a streamed call. The framework is given no endpoint, key or credential, so it cannot build another client. A function middleware (`ToolGuard`) answers every tool call from the toolbox before the framework's own argument check, so a call with arguments that are not valid is a logged, refused step; it ends the framework's loop at the step limit (`MiddlewareTermination`) and aborts the run when a tool's service gives no answer (`MiddlewareFailure`). The framework's log records, from all of its loggers, are reduced to a code and an error type. Exactly three tools are declared; no other Foundry tool, connection or context provider.
- **Stage pattern.** Key row `verdict_run` (unique on case and retriever configuration), inserted as `running`; one 180-second deadline; a repeat after the end answers the stored result with no model call; a repeat while running is 409 `in_progress`; a stale row is settled as failed with `stage_timeout` and not taken over (its steps are in the log already); a cancelled request gives the key row up. A row this build cannot run (`r3` only) is 409 `retriever_not_available` before the key row. Changed in review (triage 5), against the matrix rows "Tool's service down" and "Model unavailable": a fault that passes is not stored as a failed run. When the model is unavailable after the gateway's retries, or `extraction` or `retrieval` after the client's (two, in `adapters/dapr.py`, now also on 408 and 429), the key row is released, the steps stay in the log, and the service answers 503 `model_unavailable` or 502 `upstream_unavailable`; `workflow`'s stage retry sends the command again, and the case fails only when those retries are spent. A finish that finds its key row gone is answered the same way. A case with no facts is referred with `no_matching_rule` without a model call. The facts are read once when the run begins; `list_facts` answers that reading and marks them as listed.
- **Database.** Migration `0001`: `verdict.verdict_run`, `verdict.reason`, `verdict.agent_step`. The migrations run as the schema's owner and grant the service's role (`VERDICT_DATABASE_SERVICE_ROLE`, as `workflow` does it) SELECT and INSERT only on `agent_step`; a trigger refuses UPDATE, DELETE and TRUNCATE on it for every role. `agent_step` has no foreign key to the run, so the steps of a run that was given up stay. Locally the service signs in as the role `verdict` (`python -m verdict.local_setup`, `tools/migrate-local.sh`).
- **`workflow`.** The case status rule changed: a case whose pages are all final is `running`, not `completed`, until its verdict runs are recorded (`case_status_following(..., verdicts_recorded=)`). The orchestration, changed in place again (its header says why that was safe and how the next change must be made), commands one `run_verdict` activity per retriever configuration after the last page is final and then `complete_case`, whose store method completes the case with `case.completed` in one transaction only if every page is final and the trail holds a `verdict.suggested` event per configuration. A done run is an audit event only; a failed run fails the case; `retriever_not_available` is passed on by `StageClient` and is a permanent error (answered, not retried; the case is marked failed). `POST /cases/{case_id}/verdict-runs` (`domain/verdicts.py`) starts the orchestration `verdict_run` with instance id `<case_id>:verdict:<retriever_config>` unless there is one, and answers its state and, once it has ended, the run's id and, for a failed run, its error code from its output; 409 `pages_not_terminal` while a page is not final, while the case is not `completed` yet, and for a failed case. A run asked for afterwards is recorded and never changes the case's status. `GET /cases/{case_id}/progress` reports a case-level error code only for a failed case. No new migration.
- **Stand-in.** `synthdata.verdict_standin` plays the agent's conversation from the request's messages alone (it reads neither the answer key nor the case models): list the facts, search for each reading with the conditions on file in the query, read the rule whose band the fact meets, follow a reference a listed fact meets, answer. Modes `endless_loop`, `unseen_rule`, `wrong_effect`, `low_confidence` and `invalid_answer` beside the existing ones. 17, 18 and 15 steps for the three cases.
- **Tests.** `services/verdict/tests` (domain on fakes with an agent stub; the real framework agent on the gateway against a scripted chat-completions transport; routes; PostgreSQL, including the grants and the trigger); `services/workflow/tests/test_workflow_verdict*.py`; `packages/synthdata/tests/test_foundry_standin_verdict.py` and `test_verdict_end_to_end.py` (the real six services, the emulators, the ingested manual: `case-001` `loaded` +50 citing `UW-DM-002`, `case-002` `UW-HT-002` and `UW-TOB-001`, `case-003` `standard`, each compared with the rule table; the refer modes; the failed run; the request for one more run). - **Review fixes (triage 1 to 13).** What the notes above say, with these changes.
  - *What is stored (`domain/decide.py`, `state.py`).* A run that did not list the facts, or searched the manual for none of them, is `refer` with `low_confidence` whatever it answers: `standard` is never stored for a run that looked nothing up. A reason with a debit or a decline is kept only if its rule was read in this run, and its effect is checked against the text that read answered (a read text stands against a later search chunk); a rule a search only returned bears out "no debit". Whenever a proposed debit or decline was dropped, or an entry of the answer that is no reason did not plainly say "no effect", the run is `refer` with `no_matching_rule`. Kept reasons citing different rules of one impairment are `conflicting_rules`, whatever their facts. A final answer nested too deep to parse is `invalid_model_output`.
  - *The time budget.* `VERDICT_AGENT_TIME_BUDGET_SECONDS` (150 s; the settings refuse a value less than 10 s under the stage deadline). The domain stops the agent when it is spent, and the run is `refer` with `step_limit`, as at the step limit. Only the facts read or the storing passing the 180-second deadline is still `stage_timeout`.
  - *The step log (`domain/toolbox.py`).* A call the step limit stopped is one refused row (`step_limit`); a call cancelled or failing half way is one failed row, written whatever happens to the request. Logged arguments are plain values the database can hold (no NUL, no lone surrogate, NaN and the infinities by name, at most ten, strings cut at the longest query). A query holding a NUL is refused as invalid arguments.
  - *The gateway (`adapters/model.py`).* `GatewayClient.request`, where every call of the OpenAI client ends, raises unless the gateway itself is making the call: the Responses API, embeddings, a raw `post` or the ungated resource cannot reach the deployment.
  - *`adapters/dapr.py`.* A rule is "not defined" only on a 404 whose body is the contract's `not_found`; any other 404 is `upstream_unavailable`.
  - *`workflow`.* `WORKFLOW_AVAILABLE_RETRIEVER_CONFIGS` (default `r3`; the default configurations must be among them) names the rows a case may run with: a start naming another row is 409 `retriever_not_available` and stores nothing, and so is a request for one more run. The settings of `workflow`, `verdict` and `retrieval` each name their rows; nothing checks that they agree. `complete_case` matches the `verdict.suggested` events to the case's configurations by the detail's `retriever_config`: a run of another row, or two of one, stand in for none. `ensure_verdict_run` schedules the run again, replacing the ended instance (`replaceableStatus`), when the earlier orchestration ended with no run stored at `verdict` and not on a refusal no repeat mends; that request answers `running`. The `verdict_run` orchestration's output carries `error_code` for a failed run.
  - *Manual and stand-in.* Every definition paragraph prints when its rule applies ("Applies only to an applicant with Type 2 diabetes mellitus on file: a reading alone does not meet this rule.", "Applies to any applicant with this reading.", with ", unless ... is on file" where the rule table names one). The wording is in `manual_model.py`, read back by `verdict_standin.py`; the prompt tells the agent to apply a rule only where that sentence is met. Manual (211 pages) and rule table regenerated; a second `uv run python -m synthdata` changes nothing. With the stand-in's vectors a rule id in a sentence now finds its rule second, not first (see `deferred-work.md`).
  - *SPA.* The audit screen shows the row of a suggestion ("Made with retrieval row r3.").
- **Framework behaviours relied on** (`agent-framework-core` 1.20.0, `agent-framework-openai` 1.15.0; check them on an upgrade). Only names the package exports are imported (`Agent`, `FunctionTool`, `FunctionMiddleware`, `FunctionInvocationContext`, `MiddlewareTermination`, `MiddlewareFailure`, `agent_framework.openai.OpenAIChatCompletionClient`); no private module.
  1. `OpenAIChatCompletionClient(async_client=...)` uses the client it is given and makes each turn of `Agent.run` by one unstreamed `client.chat.completions.create(...)`. (Any other way would raise in `GatewayClient.request`.)
  2. A function middleware runs for every call of a declared tool before the framework checks the arguments, and a middleware that sets `context.result` without calling `call_next` is the tool's answer: the framework does not invoke the tool itself.
  3. `MiddlewareTermination` raised in a function middleware ends the tool loop without an error; `MiddlewareFailure` is raised out of `Agent.run` and is never turned into a tool result.
  4. `function_invocation_configuration`: `allow_concurrent_invocation: False` makes the calls of one turn in the order the model named them; `max_iterations` bounds the turns; `include_detailed_errors: False` keeps exception texts from the model.
  5. A call to a tool that was not declared is answered by the framework itself and reaches no middleware (so it is no step; triage 14).
  6. `default_options={"response_format": ...}` is sent with every chat completion.
  7. The response has `text`, `finish_reason` and `usage_details` (`input_token_count`, `output_token_count`).
  8. An error of the client is raised with the original reachable through `__cause__`, `__context__` or `inner_exception`; cancelling `Agent.run` raises `CancelledError` through it (the time budget and the deadline depend on that).
  9. The framework logs on `agent_framework` and loggers below it.
  When the framework raises anything else, the run fails with `stage_failed` and the log names the error's type (`reason=agent:<type>`), never its message.

## Design Notes

- **Where confidence comes from.** The contracts have the agent return it (`VerdictOutput.confidence`), so it is the model's own figure; the floor is applied in code. Whether that figure is meaningful is a check for the Azure session and for the bake-off's verdict accuracy.
- **The effect check reads the rule's text as the run read it**: the definition names its rating ("Probable rating: a debit of +50 %", "decline", "no debit, +0 %"). It is a guard against a made-up number, not an interpreter of the manual; keep it to those forms and drop a reason it cannot bear out.
- **Agent Framework and the gateway.** If the framework cannot take a client the gateway controls, wrap the calls so the gateway's rules still hold, and record what was done. Pins: `agent-framework-core` 1.20.0, `agent-framework-openai` 1.15.0.
- **Azure checks for `deferred-work.md`:** the agent on the real model (does it use the tools as intended, how many steps, how often it cites the unseen); the framework's calls with the service identity; token use per run against the shared limit; run time against the 180-second stage deadline; the `verdict` deploy, identity and database role step.
- The orchestration's body changes again; as in story 2.4, nothing is deployed, so it is changed in place and the notes say so.
- Do not commit or push. Scratch files go in the gitignored `.work/` folder, never outside the project. Stop any containers you start; do not run `tools/dev.sh` while another local stack holds its ports.
- No architecture principles were agreed for this project; the spine and the standards are the guardrails.
- Approval: Darrel asked on 2026-10-07 for the remaining stories to be built in order in one session; this spec was not reviewed by him before implementation, and it is over the 1,600-token target because it covers two stories and a new service.

AI Medical Underwriting Assistant: the retrieval design and how it will be judged

A proof of concept that reads a medical record, extracts the facts that move a rating, retrieves the matching rules from an underwriting manual, and suggests a verdict an underwriter can audit line by line. This page is for a reviewer who knows retrieval-augmented generation well and wants to see where the design could be wrong.

Every number on the scoreboards will come from a runner, not from this page. There are no results here, only the design and the measurement plan.

What the system does

A customer uploads a PDF. Personal identifiers are redacted first, by Azure AI Language's document redaction, and every later step reads only the redacted copy. Each page is classified as medical or not, with a confidence. Pages under 90% confidence go to an underwriter, who accepts or denies them. Facts are extracted from accepted pages, each with a page number and a verbatim quote that code checks against the page text. A verdict agent then searches the manual and suggests one of four verdicts: standard, loaded premium, decline, or refer to underwriter.

flowchart LR
  U[Upload PDF] --> P[Redact personal identifiers]
  P --> C{Classify each page}
  C -->|medical, 90% or more| E[Extract facts with page and quote]
  C -->|under 90%| Q[Underwriter triage]
  C -->|non-medical, 90% or more| A{Customer: keep or discard}
  A -->|keep| Q
  Q -->|accept| E
  E --> V[Verdict agent]
  V <-->|search, read rule| R[Retrieval: one interface, six configurations]
  V --> W[Result: PDF beside cited findings]

Redaction replaces names, addresses, phone numbers, email addresses, and identity and policy numbers with their type, such as [Person]. Dates, ages and medical terms are kept, because the rating depends on them. Each synthetic case carries planted identifiers, and the bake-off runner fails if any of them survives into stored page text.

All data is synthetic. The manual is an original 200-page document modelled on the structure of public carrier impairment guides: impairment, key questions, probable rating. It is generated from a rule table of about 40 impairments, and that table is the answer key.

Chunking the manual

Fixed chunks: the baseline

Fixed-size windows over the parsed text. They exist only so the first rung of the ladder has something honest to beat.

Smart chunks

  • One rule per chunk, cut on the manual's own structure.
  • The parent section travels with it (small-to-big).
  • An LLM-written context line says where the rule sits.

The manual is parsed once from its PDF with a layout model. One ingestion produces the chunk records and the vectors, and loads the same records into both stores, so neither store can win by indexing better text.

A chunk is tagged only with the rules it defines, never the rules it merely refers to. Without that, a cross-reference would count as a hit and inflate recall.

Embeddings are text-embedding-3-large at 3,072 dimensions. The corpus is a few hundred chunks, so both stores use exact nearest-neighbour search. Approximate indexes would add a variable and no benefit at this size.

How it is measured

Twenty synthetic cases, each with expected facts, expected rules and an expected verdict, covering all four verdicts. Two measurements are kept apart on purpose.

MetricWhat it isolatesHow
Rule recall at 5The retriever aloneOne search per expected fact, with the query built by one fixed function. A hit is the expected rule_id in the top 5.
Verdict accuracyThe whole chainEach case is uploaded once and judged six times, once per row, on the same extracted facts.
LatencyThe retrieverRetrieval time per fact, reported by the retrieval service.
Cost and effortThe running bill and the buildDeclared inputs with their sources, from current Azure price lists.

Recall is measured with a fixed query because the agent writes its own queries. If recall were read off the agent's searches, a better retriever and a better query writer would be indistinguishable.

Fairness rules

  • Same chunks, same vectors, same chat model and same embedding model for every row.
  • One search operation with one result shape; no row has its own endpoint.
  • The answer key is never indexed and no service can read it.
  • The classifier that Azure AI Document Intelligence trains is scored on pages it was not trained on.

The winner is decided on verdict accuracy, then rule recall, then latency.

The verdict agent

The fixed parts of the process (the gate, the triage wait, the audit trail) run as a deterministic workflow on Azure Durable Task Scheduler. Only the verdict stage is agentic, and it is boxed in.

Three tools, no others

  • list_facts: the case's extracted facts.
  • search_rules: free query text, through the row under test.
  • read_rule: a rule already returned by a search, or cross-referenced by a rule already read.

Rules enforced in code, not in the prompt

  • A reason is stored only if it cites a fact and a rule seen in that run.
  • No matching rule, conflicting rules, an unverified quote on a deciding fact, low confidence or hitting the step limit all force "refer to underwriter".
  • The agent cannot accept, deny or decide. The screen says "AI suggestion, not a decision".

In row r6 the agent's own search loop is switched off. Azure AI Search plans the retrieval, one request per fact, and the verdict is composed from what comes back. Otherwise the comparison would be two agents stacked on each other.

Querying the agent log

Every tool call is one append-only row: run, case, step number, tool, arguments, the fact it was about, the rules returned or read, latency and time. The demo will query it live.

Where to push on this design

  • Twenty cases is a small set. Differences of one or two cases between rows are noise, and the scoreboard should be read that way.
  • The manual is synthetic and tidy. One rule per chunk works because the manual was generated from a rule table. A real manual would chunk less cleanly.
  • Row r6 runs on a preview API and a pre-release SDK. Its behaviour and price can change.
  • Exact search hides index effects. At a few hundred chunks that is correct; it says nothing about recall under approximate search at scale.
  • The fixed query builder is a choice. Recall depends on it, and a different builder could reorder the rows.
  • Redaction can miss. The service does not read text inside embedded images, and the check only covers identifiers planted in the test cases.
  • There is no sign-in. The demo is open, with a switch between a customer role and an underwriter role. That is accepted for synthetic data only.
